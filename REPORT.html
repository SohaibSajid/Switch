3. Locks and what they protect

4. Lock order (item 10)

Whenever a thread needs more than one lock it takes them in this order and never the other way round. It is also written at the top of switch.c.

  1. ports_lock
  2. port->lock; if two ports are needed, the lower port number first (lock_two)
  3. queue->lock, never two at the same time
  4. MAC bucket locks, lowest bucket first (clear mac takes all of them)
  5. leaf locks, nothing is taken while one is held: MAC free_lock, pkt->lock, stats mutex, log lock

The commands that touch several things follow it. trunk and mirror take ports_lock, then the two ports lowest first. vlan takes the port lock and, while holding it, flushes the MAC entries of the port (buckets) and empties its queue, so no frame of the old VLAN can be queued after the command is done. shutdown takes ports_lock, the port lock (to set down), closes the queue, shuts the socket down and waits on port_cv, which releases ports_lock, until the receiver has finished. The receiver of that port does its cleanup (queue, MAC flush, join of the sender) without holding a lock and takes ports_lock only at the very end, so the admin and the receiver can never wait for each other. The forwarding path takes one port lock at a time, then the queue lock inside it; it never takes ports_lock.

5. A real bug

Symptom. After the MAC table got clear mac, the unit tests passed normally but crashed under ThreadSanitizer with CHECK failed: sanitizer_deadlock_detector.h ... (0x40, 0x40) (no data race was reported, the sanitizer itself aborted). The same would have happened to the first swctl clear mac on a TSAN build of the switch.

Cause. mac_table_clear takes every bucket lock, lowest first, so that nobody sees a half cleared table. I had raised the number of buckets to 64 to get less contention. ThreadSanitizer's deadlock detector can only track 64 locks held by one thread, so a clear with 64 buckets plus another lock hit its limit.

How I found it. By running the unit tests under -fsanitize=thread after the change (a first rebuild did not even pick the change up: the TSAN targets in the Makefile did not depend on the headers, which hid it for one run). The assert text and the value 0x40 pointed at the lock count.

Fix. 32 buckets (at most about 36 locks held together) and the reason is written next to MAC_BUCKETS; the TSAN targets now depend on $(HEADERS). A stress test (test_stress.sh) now runs clear mac, vlan, shutdown, up, mirror, SIGHUP and SIGUSR1 during traffic, and runs clean under both tools.

6. Design notes

  • Port decides the VLAN. A frame from a normal port gets the VLAN of the port (the header is rewritten before the frame is shared), so a host cannot choose its VLAN. On the trunk the frame keeps its vlan field. A known destination in another VLAN is treated as unknown and flooded inside the VLAN only. A VLAN change flushes the MACs and the queue of that port.
  • Scheduling. Weighted round robin skips empty classes. A normal or low frame older than 200 ms goes first, but never twice in a row, so a backlog of old low frames cannot block high priority.
  • Token bucket. Tokens are counted in thousandths; the bucket holds about 100 ms of frames, at least one. The timer thread refills every 10 ms and wakes the senders; the sender waits with pthread_cond_timedwait (a safety net, 100 ms) on a CLOCK_MONOTONIC condition variable. No sleep, no spinning.
  • Port semaphore and shutdown. A port that is shut down keeps (or takes) its semaphore token, up gives it back, so the semaphore always equals the number of free usable ports and an extra host gets switch full exactly when it should.
  • Mirroring copies into the sniffer's bounded queue, so a slow sniffer costs only copies. A sniffer that is a normal recipient of the frame gets it once.
  • Shutdown order. The signal thread only sets stopping and wakes the poll loops; the main thread then joins waiters, receivers (which join their senders), the helper threads and the logger last, and frees the table and the queues.
  • Two switches. The pipe link is one more port (the trunk). A pipe has no shutdown(), so its threads wait with poll() on the pipe and on a wake-up pipe.
  • Supervisor. The MAC table is a fixed pool of entries linked by index, so it can live in shared memory. After a crash the new switch walks the table, drops broken entries, and rebuilds counters and the free list. A frame for a MAC that is still in the table but has no host any more is flooded, not dropped.

7. Benchmark: which lock for the MAC table

bench runs 1 to 16 threads on one hash table (4096 MACs), each doing lookups and learns for 2 seconds. Same table, only the locking differs.

threads (10% learns), million ops/s124816
one global lock4.152.111.040.740.73
striped locks4.254.474.394.395.34
read-write lock4.000.480.580.590.63

With one thread the three are the same. The global lock gets slower with every thread (the threads wait for each other, and the lock bounces between cores). Striped locks keep their speed, about 6 to 7 times the global lock from 8 threads. The read-write lock is the worst with 10% writes: every learn stops all readers, and it is not better than a plain mutex until writes are rare (1%: 1.5 to 1.7 against 0.65 for the global lock, but still behind striped at 3.7 to 4.3). Striped locks do not get faster with more threads on this machine (a laptop CPU under WSL2). The reason is not the table: with no learns and no LRU stamp the curve stays flat; each lock and unlock writes to the lock's cache line. That is why the switch uses striped locks.
